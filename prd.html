Title: ChainMind Synapse 6-hour clock Two-chain minimum No centralized IdP

Background

In decentralized digital identity, users hold multiple credentials across different blockchains. Those credentials have different validity windows and different issuer trust. Identity is fragmented. No current system provides a real-time, AI-driven reconciliation of conflicting claims about a user’s identity status. Adjacent products exist (wallet reputation, DID/VC standards, oracle plumbing, bot scoring). They do not close this gap. See PROPOSAL.html and research-existing-solutions.md.

Problem statement (verbatim intent)

When a user presents a credential from one blockchain to a service provider on another, the provider cannot verify current validity or detect conflicting claims from other chains. That creates a trust gap and manual overhead.

In 6 hours the team must build a system that:

  1. Ingests real-time credential claims from multiple blockchains.
  2. Uses AI to assess credibility.
  3. Generates a unified, explainable identity state.
  4. Makes that state auditable and tamper-proof.

Scope

  • Process blockchain identity claims.
  • Apply AI-based trust scoring.
  • Produce a unified identity state.
  • Deployable on-chain, real-time updates.
  • Must not rely on centralized identity providers.

MVP scope (must ship)

#PRD lineHow we implement it
M1 Ingest identity claims from two blockchain sources (e.g. Ethereum and Polygon) via smart contract events or RPC calls Deploy ClaimSource on Ethereum Sepolia and Polygon Amoy. Watch ClaimPosted / ClaimRevoked with web3.py or viem. Also support a one-shot RPC backfill of logs.
M2 Use a Gen-AI agent to analyze claim content and extract trust signals (issuer reputation, expiration, revocation status) Prompt-orchestrated extractor (Instructor or DSPy). Output is a typed NormalizedClaim. No weights are trained on the LLM.
M3 Apply an AI-ML model to score each claim’s credibility based on historical data and contextual features sklearn.ensemble.HistGradientBoostingClassifier (or LogisticRegression if data is tiny) trained on a generated labeled set. Persist with joblib.
M4 Store the final identity state on a blockchain ledger with timestamped, immutable records IdentityState.commit(subject, stateHash, scoreBps, modelVersion) on Sepolia. Records are append-only. Previous commits remain.
M5 Expose a REST endpoint that returns the current identity state and a confidence score GET /v1/identity/{subject} on FastAPI. JSON includes sources and per-claim scores. p95 < 500 ms from cache / last commit.

Functional requirements

  1. Parse blockchain identity claims from at least two chains.
  2. Extract and normalize claim metadata using Gen-AI prompt engineering.
  3. Train or use a pre-trained AI-ML model to score claim credibility.
  4. Generate a unified identity state with confidence metrics.
  5. Store the final state on-chain with timestamped, immutable records.
  6. Expose a REST API to query the current identity state.
  7. Provide a JSON response with claim sources and trust scores.

Acceptance tests for each line live in REQUIREMENTS.html.

Constraints

  • Built within 6 hours.
  • All blockchain interactions on testnets. PRD examples: Goerli, Mumbai.
  • No external identity providers or centralized databases.
  • All Gen-AI components use prompt orchestration, not fine-tuning.
  • AI-ML model trained or deployed with existing libraries (scikit-learn, Hugging Face).
  • No pre-built identity reconciliation tools or commercial SDKs.

Constraint interpretations you must follow

Goerli and Mumbai are dead. Ethereum Foundation sunset Goerli after Dencun (validators exited around April 2024). Polygon Mumbai used Goerli as its root chain and was deprecated on 13 April 2024 in favor of Amoy (chain id 80002, Sepolia-anchored). Building on the named examples will fail. Use Sepolia + Amoy and state the substitution in the demo. Sources: Ethereum Foundation Goerli LTS, Polygon Amoy announcement.

“No centralized databases” means the identity state is not authoritative in Postgres/Firebase/Supabase. A local JSON/SQLite cache for the API read path is allowed if every served state is recoverable from chain events + the committed hash. Do not put issuer or subject PII in a hosted DB.

“No external identity providers” means no Civic, Worldcoin, Coinbase Attestations-as-IdP, Google/Apple login as the identity, no KYC vendor. A public RPC is not an identity provider. A faucet is not an identity provider.

“No commercial identity reconciliation SDKs” means do not call Trusta, Nomis, RubyScore, Ethos, Cred, UTU, or Gitcoin Passport APIs to produce the score. OpenZeppelin, viem, web3.py, sklearn, and W3C DID/VC libraries are building blocks, not reconciliation products.

“Prompt orchestration, not fine-tuning” forbids LoRA, SFT, DPO, and “we trained a small judge.” CRAVE (2025) uses a fine-tuned SLM judge — copy the conflicting-perspective prompting, not the fine-tune.

Deliverables

  1. Working demo of the system on a testnet (two testnets).
  2. Live API endpoint that returns identity states.
  3. Gen-AI explanation of the trust decision.
  4. A blockchain transaction showing the final identity state.
  5. A 3-minute demo video showing the full flow.

Personas the PRD implies

Holder

A user with did:ethr:sepolia:0x… who has posted or been issued claims on two chains. They want one status they can show a relying party.

Relying party

A service on chain B. They hit GET /v1/identity/{subject}, read confidence, verdict, conflicts, and the commit tx. They re-verify the hash if they are paranoid.

Issuer

An address that signs claims. Their historical true-positive / false-positive rate becomes Beta evidence. They are not a centralized IdP; anyone can issue; we score them.

Non-goals (6-hour cut)

  • Mainnet, bridges, or moving assets.
  • Full SSI wallets, DIDComm, ION, Ceramic, ACA-Py as runtime dependencies.
  • Zero-knowledge selective disclosure (mention in RESEARCH, do not implement unless bonus time).
  • ERC-8004 agent identity as the product (adjacent 2025/26 standard; optional footnote).
  • Production key custody, multisig, or account abstraction.
  • Training foundation models or hosting GPUs.

Success looks like

A judge pastes a subject address. The API returns two-chain claims, at least one engineered conflict (e.g. “over 18” vs “under 18”, or “KYC-active” vs “KYC-revoked”), a fused confidence, a prose explanation that cites issuer reputation + expiry + revocation + conflict, and a Sepolia tx whose logs match stateHash. Accuracy on the held-out synthetic set prints > 75%. A 3-minute take records the whole path.
